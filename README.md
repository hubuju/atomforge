> 一个可运行的 **Atoms Demo**：用一句自然语言描述需求，多智能体协作生成一个真正能跑的网页应用，右侧沙箱即时渲染，多轮迭代、版本回滚、自动查错修错，最后一键发布成免登录可访问的公开链接。

- **在线体验**：https://atomforge-297572-11-1303973043.sh.run.tcloudbase.com
- **源码仓库**：https://github.com/hubuju/atomforge
- **测试账号**：无需预置，落地页可直接注册（名称 + 两次密码，无邮箱、无验证码）；也可「游客体验」一键进入

## 1. 30 秒看懂它做什么

AtomForge 把「AI 生成代码」这件事拆成了一条**可观察、可干预、可回退**的流水线，而不是一个黑盒的聊天框。

```
用户一句话需求
      │
      ▼
┌─────────────┐   规格（界面/数据/交互/文件划分）
│  规划者 Planner │ ──────────────┐
└─────────────┘                │  ← 用户可在此暂停、审阅、直接改规格
      │                        ▼
      ▼                  [ 规格确认闸门 ]
┌─────────────┐                │
│  实现者 Coder  │ ← 按文件逐个生成，不是一次吐一大坨
└─────────────┘
      │  多文件项目（index.html / styles.css / app.js …）
      ▼
┌─────────────┐   带严重度与文件定位的问题清单
│ 审查者 Reviewer│
└─────────────┘
      │
      ▼
┌─────────────┐   只重写被点名的文件
│  修复者 Fixer  │ ←──── 轮次有硬上限，不会无限打转
└─────────────┘
      │
      ▼
规则化体检（静态审计 + 沙箱运行探针）→ iframe 实时预览 → 落库为版本快照
      │
      ▼
一键发布 → /s/:slug 免登录直接运行
```

四个角色的执行过程在界面上以**泳道**形式实时呈现：每个角色用了哪个模型、当前在做什么、耗时多久、产出多少字符，展开还能看到它收到了什么上下文、交出了什么结果。这是本项目最想传达的一点——**Agent 的过程本身就是产品的一部分**。

## 2. 建议的体验路径

从零到看到成果大约 2 分钟：

1. 打开在线链接 → **注册**（起个名字 + 设两次密码即可）
2. 点「新建应用」→ 可以直接从 **6 个内置模板**起步，也可以自己写需求
3. 写一句需求，例如「做一个番茄钟，能设置工作和休息时长，结束时有提示音」
4. 观察 **规划者** 产出的规格 → 确认或直接编辑它 → 开始实现
5. 在 **角色泳道** 里看四个角色依次接力，右侧 **代码面板** 逐文件流式写入
6. 生成结束后右侧自动切到 **预览**，直接点按钮试玩
7. 再补一句「加一个今日完成次数统计」→ 体验**增量迭代**（只改该改的文件）
8. 打开 **版本** 列表 → 一键回滚到上一版 → 再切回来
9. 点 **发布** → 拿到公开链接 → 用无痕窗口打开，未登录也能直接运行

想看延展能力，可以故意在代码面板里改坏一行 JS 并点「运行」，会捕获到真实运行时错误并弹出红色横幅，点「让 AI 修复」即可形成闭环。

## 5. 实现思路与关键取舍

这一节是我认为最值得读的部分。下面每一条都是开发过程中真实发生过的**方案调整**，而不是事后补写的设计说明。

### 取舍一：生成产物形态 —— 从「单文件 HTML」改成「多文件项目」

**最初的选择**是让模型输出一个自包含的单文件 HTML（内联 style 和 script）。理由很实在：iframe 里直接能跑，完全绕开容器沙箱、依赖安装、构建链这一整套复杂度，在有限时间内是最稳的交付路径。

**但很快暴露两个问题**：一是单文件动辄上千行，模型经常写到一半被输出上限截断；二是用户想改点东西时，面对一坨混在一起的代码根本无从下手。

**最终方案**是让模型按 `<<<FILE path="...">>>` 协议逐个文件输出真正分离的 `index.html` / `styles.css` / `app.js`（上限 6 个文件），**内联只发生在预览打包阶段**——`lib/bundler.ts` 在渲染前把本地引用内联成单文档，源码始终保持分离。

这样同时拿到了三个好处：源码可读可改、单次输出不易截断、预览依然零依赖即时可跑。代价是多了一层打包逻辑，需要处理「本地资源要内联但 CDN 链接不能动」「引用了不存在的文件时不能把标签吞掉」这些边界，这部分现在有专门的测试守着。

### 取舍二：生成方式 —— 从「一个大提示词」改成「四角色流水线」

**最初的做法**是一个 system prompt + 把当前代码作为上下文、要求整份重写。单文件时代这套逻辑够用。

**改成多文件后问题就大了**：一次调用要同时完成「理解需求 → 设计结构 → 写完所有文件 → 自我检查」，模型容易漏需求、写到后面忘了前面的约定，更糟的是**增量迭代时会顺手改坏上一轮已经正确的代码**。

**最终方案**是拆成四个角色，每个角色只干一件事：

- **规划者**只输出结构化规格（界面 / 数据 / 交互 / 文件划分），不写代码
- **实现者**按文件逐个调用，一次只专注一个文件
- **审查者**输出带严重度和文件定位的问题清单，不写代码
- **修复者**只重写被点名的文件

这里有两个刻意的设计：

1. **角色间通过「黑板」共享状态，而不是传递对话历史**。黑板上放规格、文件集、问题清单，每个角色只读它需要的那部分。这让每次调用的上下文都短得多，职责边界也清晰。
2. **修复者只碰被点名的文件**。这天然实现了「局部修改」，是解决前面「改坏上一轮成果」的关键。

### 取舍三：把「规格确认」做成闸门，但允许关掉

规划者出完规格后，流水线**会停下来等用户确认**，而且规格是可以直接编辑的——想改布局、想加字段、想调整文件划分，改完再开工，比生成完了再返工便宜得多。

但我很清楚这会打断流畅感。所以它是**一个默认开启的开关**：想要可控就开着，想要一句话到底就关掉，关掉后自动继续。这类「既要可控又要流畅」的矛盾，我倾向于给开关而不是替用户做决定。

### 取舍四：自检做两层 —— 模型审查 + 规则兜底

审查者是模型，模型会误判，也可能输出不可解析的格式。所以在它之外**保留了一层规则化体检**：静态审计（引用是否存在、脚本是否被截断、按钮是否绑了事件、括号是否配平）加上沙箱运行探针（注入 `window.onerror` 捕获真实运行时错误），两边结果合并成一份报告。

两层是互补关系：模型负责语义层面「这个实现对不对」，规则层保证「基础缺陷一定被发现」。规则层还有个额外价值——它的输出是确定的，因此可以直接拼成修复提示词交给 AI，形成闭环。

写这层的时候我特别注意了**误报**问题。比如「括号是否配平」这条规则，如果简单地数括号，字符串和注释里的括号就会造成误判，反而比不检查更糟。所以测试里每条规则都做了双向验证：既要能抓到真缺陷，也不能在健康代码上报警。

### 取舍五：模型配置只允许覆盖 model id

设置面板支持给每个角色单独指定模型——推理型模型做规划、代码型模型做实现、便宜的模型做审查，这是很自然的需求。

但**角色覆盖只允许改 model id，传输方式、API Key、温度一律共用全局配置**。原因是如果允许每个角色配一套完整连接参数，用户很容易配出一个连不通的组合，而排查成本极高。限制成只覆盖 model id，混合模型的收益拿到了，连通性风险为零。

### 取舍六：公开分享走后端免鉴权路由

发布出来的应用必须让**未登录访客**能直接打开。访客手里没有 token，前端的数据查询走不通。所以专门开了一条 `GET /api/v1/share/{slug}` 的免鉴权路由，服务端按 slug 校验发布状态后返回文件集。

这条路由的边界处理写得比较克制：slug 为空返回 400，项目不存在或未发布统一返回 404（不区分，避免探测），已发布但还没生成内容也返回 404。**不会因为查询不到就泄露任何内部信息。**

### 取舍七：代码高亮自己写词法分析，不引入编辑器

代码面板只需要**只读的美观展示**（行号 + 语法着色 + 流式光标），并不需要编辑器的自动补全、多光标、LSP 那些能力。引入 Monaco 会带来几百 KB 的体积，Prism 也要拖一套主题体系。

所以给 HTML / CSS / JS 各写了一套轻量 tokenizer。代价是着色精度不如成熟方案，但对「看懂 AI 写了什么」这个目标完全够用，而且首屏体积没有任何负担。

### 取舍八：版本保留上限，但带备注的永不清理

每轮生成都落快照，项目迭代十几轮后版本列表会失控，存储也会膨胀。所以加了保留上限（5–50，默认 20），超出后服务端自动清理最旧的。

但这里有个细节：**用户手动加了备注的版本会被钉住，永远不参与清理**。逻辑很简单——用户愿意花力气给一个版本起名字，说明这一版对他有意义，那它就不该因为「太旧」被删掉。

### 一个被测试逮到的真实缺陷

补单元测试的时候跑出一个隐藏得很好的 bug：读取配置时用了 `Number(parsed.versionKeep)`，而 `Number(null)` 等于 0，会被区间夹取成最小值 5。表现出来就是**用户从没设置过，却看到保留上限是 5**，像是自己选的。

修法是加一层先判空的取值函数，区分「未配置」和「非法值」两种情况，缺失时回落默认值而不是先转成 0 再夹取。`temperature` / `maxFiles` / `maxRepairRounds` 有同样的问题，一并修了。

这个 bug 靠手点几乎不可能发现——它的表现太合理了。这也是我认为这套测试值得写的原因。

### 明确未完成

| 项 | 现状 | 影响 |
|----|------|------|
| **生成中断恢复** | 未实现 | 生成过程中刷新页面或网络断开，这一轮的进度会丢失，需要重新发起。已落库的历史版本不受影响 |
| 生成产物的能力边界 | 仅静态前端 | 生成的应用不能有自己的后端和数据库，复杂需求（如带登录的多人应用）无法真正跑通 |
| 协作与权限 | 未实现 | 项目是单人的，没有共享编辑、没有只读协作者 |
| 移动端工作台 | 未适配 | 预览面板支持切换手机视口，但工作台本身在小屏上体验不佳 |
| 生成成本可见性 | 未实现 | 不显示每轮消耗的 token 与费用 |
| 测试范围 | 仅核心逻辑层 | 有单元测试，但没有端到端测试覆盖完整用户流程 |

**为什么中断恢复没做**：它需要把生成过程的中间态（当前在哪个角色、已完成哪些文件、黑板内容）持续落库，还要处理重入时的去重与冲突。这个改动会渗透到编排器和工作台的状态管理，评估下来不是能安全塞进剩余时间的量。相比之下我选择先把「已完成的每一轮都可靠落盘、可回滚」做扎实——即使中断，用户也不会丢掉任何已经成功的成果。

## 7. 如果继续投入，我会怎么扩展

按**投入产出比**而非技术趣味排序：

### P0 — 补完可靠性短板

1. **生成中断恢复**。把编排器的中间态落库，刷新后能从上一个完成的角色继续，而不是从零重来。这是当前唯一会让用户丢失工作的场景，优先级最高。
2. **端到端测试**。核心逻辑有单测了，但「注册 → 生成 → 发布」这条链路目前靠人工回归。上一套 Playwright 流程测试，改动才敢放心。

### P1 — 打开能力天花板

3. **让生成的应用拥有后端**。这是当前最大的能力边界。可行路径是给生成的应用分配一组受限的数据表和一个免鉴权只读接口，让它能真正存数据。这会把可生成的应用类型从「静态工具页」扩展到「有真实数据的小应用」，是价值最大的一步，但复杂度也最高。
4. **角色可编辑**。现在四个角色的提示词是写死的。开放让用户改提示词、增删角色（比如加一个「无障碍审查者」），这个平台就从工具变成了框架。

### P2 — 提升日常体验

5. **生成成本面板**。显示每轮每个角色的 token 与费用，混合模型策略才有依据去调优。
6. **对话内引用**。允许用户选中预览里的某个元素直接说「这个按钮太小了」，比用文字描述位置精确得多。
7. **项目共享与协作**。只读协作者 → 评论 → 共享编辑，按这个顺序递进。

### 我不会优先做的

- **支持更多前端框架**（React / Vue 产物）。听起来很有价值，但一旦引入构建链，「即时预览」这个核心体验就要重做成容器方案，收益远不及成本。
- **更炫的界面动效**。当前视觉已经能支撑「这是个可用的专业工具」这个判断，继续投入的边际收益很低。

## 8. 本地运行与测试

### 前端

```bash
cd app/frontend
pnpm install
pnpm run dev        # 开发服务
pnpm run lint       # 代码检查
pnpm run build      # 生产构建
pnpm run test       # 单元测试（116 个用例）
pnpm run test:watch # 开发时监听模式
```

### 后端

后端已完全自托管：数据库为 SQLite 单文件，AI 生成走后端中转（默认 DeepSeek），与 Atoms Cloud 无任何运行时依赖。

```bash
cd app/backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
export DATABASE_URL=sqlite:///./data/atomforge.db     # PowerShell: $env:DATABASE_URL="..."
export APP_AI_BASE_URL=https://api.deepseek.com/v1
export APP_AI_KEY=sk-...                              # 你的 DeepSeek Key
uvicorn main:app --host 0.0.0.0 --port 8000
```

### 一键部署（线上体验）

生产环境用 Docker 单容器同时托管前端页面与后端 API，详见 [DEPLOY.md](./DEPLOY.md)：

```bash
cp .env.example .env   # 填入 APP_AI_KEY
docker compose up -d --build   # 打开 http://localhost:8000
```

## 关于这个 Demo 的一句话总结

如果只能保留一个设计，我会保留**四角色流水线加上规格确认闸门**。因为它回答的不是「AI 能不能写代码」这个已经有答案的问题，而是「**当 AI 写错了，用户能在哪一步、用什么代价把它掰回来**」——这才是这类产品真正的护城河所在。
